# 05 - Hermes curator guardrail rules

Source: `~/.hermes/hermes-agent` (Hermes Agent v0.14.0, read-only). Core files: `agent/curator.py` (1781 lines, the orchestrator), `agent/curator_backup.py` (696 lines, snapshot/rollback), `tools/skill_usage.py` (608 lines, telemetry + provenance), `tools/skill_manager_tool.py` (the `skill_manage` tool the reviewer calls), `tools/skill_provenance.py` (78 lines, the write-origin context var), `cron/jobs.py` (`rewrite_skill_refs`), and the two trigger sites in `cli.py` (~line 12190) and `gateway/run.py` (~line 17845). Cross-checked against `website/docs/user-guide/features/curator.md` and test names under `tests/agent/test_curator*.py`, `tests/hermes_cli/test_curator*.py`.

Two things in here contradict what the shipped docs and the reviewer's own prompt claim. Both are called out explicitly rather than smoothed over, because D15 says Hydra copies rules, not code, and a rule that doesn't hold in the code it came from is worth knowing before it gets copied.

## What triggers a run, and what stops one

Two call sites, both gated by the same function, `agent.curator.maybe_run_curator()`:

- CLI session start (`cli.py`), passing `idle_for_seconds=float("inf")` with the comment "CLI startup = fully idle."
- The gateway's cron-ticker thread (`gateway/run.py`), polling every 60 ticks (`CURATOR_EVERY = 60`, roughly hourly at the ticker's own interval) and also passing `idle_for_seconds=float("inf")`.

`maybe_run_curator` checks `should_run_now()` (enabled, not paused, `last_run_at` older than `interval_hours`, default 168h/7d) and then, only if the caller supplied a real idle measurement, `min_idle_hours` (default 2h). Both production call sites pass infinity, so in this build `min_idle_hours` is a config knob with no live enforcement path. It's checked in code (`agent/curator.py:1774-1777`), but nothing currently calls it with a real idle duration. Worth knowing before assuming the config value does anything.

First-run behavior is deliberately not "run immediately once due": when `last_run_at` is absent, `should_run_now()` seeds it to now and returns `False`, deferring the first real pass by one full interval. `hermes curator run --dry-run` bypasses this gate on request.

Nothing stops a run once the LLM pass starts. `hermes curator pause` only blocks the *next* trigger; it doesn't touch a pass already in flight, and there's no cancellation hook in `_run_llm_review`. The only real bounds are a per-call HTTP timeout on the aux-model requests (`auxiliary.curator.timeout`, default 600s per docs), a `max_iterations=9999` ceiling that exists as a backstop but is high enough the model is expected to self-terminate long before hitting it, and process exit (CLI closes, gateway restarts), which kills the daemon thread outright mid-mutation with whatever the model had already done left in place.

## How staleness, overlap, and obsolescence are decided

Staleness and archival are two *separate* mechanisms with different evidence:

**Deterministic (no LLM), `apply_automatic_transitions()`:** the anchor timestamp is the latest of `last_used_at` / `last_viewed_at` / `last_patched_at` (`skill_usage.latest_activity_at`), falling back to `created_at` if the skill was never touched (so a brand-new skill isn't instantly stale). `anchor <= now - archive_after_days(90)` archives; `anchor <= now - stale_after_days(30)` and currently active marks stale; a skill that gets used again after going stale flips back to active. Pinned skills are skipped outright.

**LLM overlap/consolidation judgment:** the prompt explicitly forbids using the usage counters as evidence here. "`use=0` is not evidence a skill is valuable; it's absence of evidence either way" and "DO NOT use usage counters as a reason to skip consolidation." Instead the reviewer is told to scan for prefix/domain clusters (`hermes-config-*`, `gateway-*`, etc.), and for each cluster ask "would a human maintainer write this as N separate skills, or as one skill with N labeled subsections?" A narrow name, one containing a PR number, an error string, a feature codename, or an "audit/diagnosis/salvage" session artifact, is itself treated as evidence the skill belongs folded into an umbrella, regardless of how much it's been used.

**Obsolescence (prune with no merge target):** left entirely to model judgment, no counters, no rule beyond "truly stale, irrelevant, or obsolete." What's enforced is the *paper trail*, not the judgment: every `skill_manage(action="delete")` call must carry `absorbed_into=<umbrella>` or `absorbed_into=""`, and that argument (not the model's prose) is what the downstream classifier trusts.

## Which model reviews, and how it's prompted

Resolved through the standard auxiliary-task slot machinery, same as Vision, Compression, Session Search, etc.: `auxiliary.curator.{provider,model}`, falling back to a deprecated one-off `curator.auxiliary.{provider,model}` block, falling back to whatever the main chat model is if left `auto` (`agent/curator.py:_resolve_review_runtime`, lines 1557-1600). Nothing is hardcoded to a specific model. The docs' example (`google/gemini-3-flash-preview` via openrouter) is just an example of running the review on something cheaper than the main chat model.

The full system/user prompt is `CURATOR_REVIEW_PROMPT` in `agent/curator.py`, lines 330-445 (about 1,000 words). It opens by rejecting the obvious framing:

> "This is an UMBRELLA-BUILDING consolidation pass, not a passive audit and not a duplicate-finder... A collection of hundreds of narrow skills where each one captures one session's specific bug is a FAILURE of the library — not a feature."

Hard rules given to the model, verbatim:

> "1. DO NOT touch bundled or hub-installed skills... 2. DO NOT delete any skill. Archiving (moving the skill's directory into ~/.hermes/skills/.archive/) is the maximum destructive action. Archives are recoverable; deletion is not. 3. DO NOT touch skills shown as pinned=yes... 5. DO NOT reject consolidation on the grounds that 'each skill has a distinct trigger'. Pairwise distinctness is the wrong bar."

And a floor on how much it's expected to do:

> "If you end the pass with fewer than 10 archives, you stopped too early — go back and look at the clusters you left alone."

The dry-run variant prepends a banner (`CURATOR_DRY_RUN_BANNER`, lines 303-327) that lists forbidden actions in the same prompt and tells the model to self-report if it slips: "If you accidentally take a mutating action, say so explicitly in the summary so the reviewer can revert it." That sentence is the whole enforcement mechanism. See the gap below.

## What the snapshot captures, and where it lands

Before every *real* (non-dry-run) pass, `agent.curator_backup.snapshot_skills()` writes a tar.gz to `~/.hermes/skills/.curator_backups/<utc-iso-id>/skills.tar.gz`, alongside `manifest.json` (reason, timestamp, byte size, skill-file count) and a separately-captured copy of the live `~/.hermes/cron/jobs.json` as `cron-jobs.json`. It excludes `.curator_backups/` itself (recursion) and `.hub/` (hub-managed, rolling it back would violate the hub's own lockfile invariants), and includes `.usage.json`, `.archive/`, `.curator_state`, and `.bundled_manifest` so a rollback rehydrates provenance and scheduler state consistently, not just skill content. Snapshots are pruned to `curator.backup.keep` (default 5), newest kept.

Rollback (`agent.curator_backup.rollback()`) is itself made undoable: step one is *another* snapshot of the current tree tagged `pre-rollback to <target-id>`, taken before anything is touched. Extraction rejects any tar member with an absolute path or a `..` component, and prefers Python 3.12+'s `filter="data"` safer extraction. Cron restoration is surgical: only the `skills`/`skill` fields on jobs matched by id are overwritten, and schedule, `next_run_at`, `enabled`, and prompt are left as live state.

## Failure modes the authors guarded against

Each of these cites the code comment or test naming the incident, not just the fix:

- **Curator firing on a brand-new or freshly-migrated library before the user ever saw it.** `hermes_cli/main.py`'s `_print_curator_first_run_notice` describes the bug directly: "exactly the window where the gateway ticker used to fire Curator against a fresh skill library immediately after an update." Fixed by the seed-and-defer-one-interval behavior in `should_run_now()`.
- **The model forgets to emit the structured YAML summary, or the summary doesn't match what it actually did.** Named directly in `tests/agent/test_curator_classification.py`: "This is the exact #18671 regression: the model forgets to emit the YAML..." Fixed by making the `absorbed_into` argument on the delete call itself the authoritative signal, not prose, not a parsed summary block, with the YAML block and a tool-call-content heuristic as fallback layers in strict precedence order (`_reconcile_classification`).
- **The model claims a merge target that doesn't exist.** `_delete_skill` (`tools/skill_manager_tool.py`) validates the `absorbed_into` target is a real skill on disk before allowing the delete; `_reconcile_classification` separately downgrades any hallucinated claim that slips through anyway rather than trusting a broken reference.
- **Cron jobs silently losing their instructions after a consolidation.** `cron/jobs.py` states it outright: a job listing a skill by name that no longer exists just "goes off... quietly. See issue #16265." Fixed by `rewrite_skill_refs()`, which every consolidating run calls to patch affected jobs' skill lists in place.
- **A bad rollback becoming itself unrecoverable.** Fixed by always snapshotting the pre-rollback state first, so a rollback can be rolled forward.
- **A transient disk error on the pre-run snapshot permanently disabling the curator.** The comment in `run_curator_review` states the tradeoff explicitly: a failed snapshot logs at debug and the run proceeds anyway, "the alternative is that a transient disk issue silently disables curator forever, which is worse."
- **The review fork recursing into its own self-improvement nudge.** Guarded by zeroing `_memory_nudge_interval` and `_skill_nudge_interval` on the curator's forked agent.
- **A crash mid-review corrupting the schedule.** `last_run_at` and a summary are persisted to `.curator_state` *before* the LLM pass starts (real runs only; dry-run never advances `last_run_at`), so a crash mid-pass still records the run and doesn't cause an immediate re-fire on the next tick.

## Two places where the guard is weaker than it's advertised as

**"Archive" via the LLM path is not the same operation as "archive" via the automatic path.** The automatic staleness sweep (`apply_automatic_transitions`) calls `skill_usage.archive_skill()`, which does a real directory move into `.archive/`, genuinely recoverable via `hermes curator restore <name>`. But the prompt tells the reviewing model to use `skill_manage(action="delete")` for consolidation removals, describing it as "archive a skill" (`agent/curator.py:408`), and that tool's actual implementation (`tools/skill_manager_tool.py:_delete_skill`, line 700) calls `shutil.rmtree(skill_dir)`, a real filesystem delete, not a move. `skill_usage.archive_skill()` is called from exactly three places in the whole codebase (`hermes curator archive`, `hermes curator prune`, and the automatic sweep), never from the LLM's delete path. So for anything the reviewer consolidates or prunes, the "archives are recoverable" guarantee the prompt states as a hard rule doesn't hold at the per-skill level. The only real safety net is the pre-run whole-tree snapshot, recoverable only by rolling back the *entire* run via `hermes curator rollback`, not by restoring the one skill.

**Dry-run's no-mutation guarantee is prompt text, not a code-level block.** The per-turn background-review fork (`agent/background_review.py`) enforces its tool boundary at the dispatch layer: `set_thread_tool_whitelist()` restricts it to memory and skill tools only, denying everything else at runtime regardless of what the model tries. The curator's review fork has no equivalent call anywhere in `agent/curator.py`. Dry-run relies entirely on the banner text telling the model which actions not to take, and its own fallback is "say so in the summary" if it slips. The same fork also calls `terminal` (per the prompt's own toolset list, for `mv`-into-archive operations) without installing the non-interactive approval callback that `background_review.py` explicitly installs for the identical tool, citing a real deadlock this exact pattern caused elsewhere (issue #15216: a dangerous-command approval prompt falling back to `input()` on a background thread with no attached TUI). Nothing in the curator path shows this has actually hung yet, but the sibling code in the same file family needed the fix, and the curator fork didn't inherit it.

## Rule list for Hydra's curator, each with its reason

1. **Scope to skills your own background loop created, not "not bundled/not hub."** `list_agent_created_skill_names()` requires a `created_by == "agent"` marker (`_is_curator_managed_record`), and `mark_agent_created()` is only called when `tools.skill_provenance.is_background_review()` is true at creation time, meaning only skills born from the autonomous self-improvement fork, never a skill the user or a foreground turn asked the agent to write. Reason, straight from the comment: "foreground `skill_manage(create)` calls are user-directed, and those skills belong to the user (the curator must not touch them)." This is a stricter, three-way provenance test than the shipped docs describe (docs say "binary, bundled/hub vs. everything else"; the code is not).
2. **Never touch a pinned skill, in either the deterministic sweep or the LLM pass, but let patches through on pinned skills.** Reason: pin exists to stop irrecoverable loss (archive/delete), not to freeze content the agent could still usefully improve. Codified once (`_pinned_guard`) and enforced at the tool layer, not just by prompt instruction, unlike most of the other rules here.
3. **Anchor staleness on activity (view/use/patch), not creation, and fall back to creation only when there's never been activity.** Reason: without the fallback, a skill nobody has touched since it was written would never anchor to anything and would be immortal; without excluding creation from the normal anchor, a skill that's actually being used would still look "stale" relative to when it was made.
4. **Never let usage counters gate a consolidation decision.** Reason, quoted from the prompt: counters are sparse and new, so zero use is "absence of evidence either way," not evidence of irrelevance. Overlap is a content judgment, not a frequency judgment.
5. **Require the model to declare its own intent (`absorbed_into=<target>` or `absorbed_into=""`) at the moment of each deletion, and treat that declaration, not a parsed post-hoc summary, as authoritative.** Reason: this is the direct fix for a real regression (#18671) where the model's free-text summary didn't reliably match its actions. Ask for the classification at the point of the action, not after.
6. **Validate any model-declared merge target exists before allowing the removal, and independently re-check it against what still exists after the run.** Reason: guards against the model hallucinating an umbrella that was never created or that got removed later in the same pass.
7. **Snapshot before every mutating pass, never before a preview, and make rollback itself reversible by snapshotting again before restoring.** Reason: a rollback that can't itself be undone turns one mistake into two.
8. **Treat a failed snapshot as a warning, not a reason to refuse the run.** Reason, stated directly in the source: silently disabling the whole feature on a transient disk hiccup is worse than proceeding once without a safety net.
9. **Exclude anything hub-managed from both the snapshot and any rollback.** Reason: the hub keeps its own lockfile invariants; overwriting hub-installed content from a curator snapshot would desync it from the hub's own state.
10. **Rewrite any other subsystem's references to a skill by name whenever that skill is consolidated or pruned, as part of the same run.** Reason, directly from a bug: a scheduler (or anything else) that looks up a skill by name and just skips silently on a miss is a duty that quietly stops firing after a rename, with no error anywhere pointing at the curator as the cause (#16265).
11. **Defer the first-ever run by a full interval instead of firing on the first opportunity, and let the user preview with a dry-run before that window closes.** Reason: fixed a real incident of the curator hitting a just-migrated or freshly-installed library the user hadn't had a chance to look at yet.
12. **Make the deterministic (staleness/archive) transitions independent of, and run before, the LLM judgment pass, and always let a reactivation reverse a stale mark.** Reason: state that can only move one direction (active → stale → archived) punishes a skill for a temporary lull; letting fresh activity pull it back to active is what makes "stale" a safe, low-stakes label instead of one you have to guard against ever applying.
13. **If your curator can call anything shell-like, install a non-interactive approval/deny callback on that fork before it runs, unconditionally.** Reason: this is not something Hermes' curator does today, but it is something the sibling background-review fork in the same codebase had to learn the hard way (#15216, an approval prompt deadlocking on a background thread with no TUI attached). Don't wait to hit the same bug twice.
14. **Make "archive" and "delete" the same operation everywhere in the tool, or don't call the destructive one "archive."** Reason: this is the one rule Hermes' own code violates. The automatic sweep's archive is a real, individually-recoverable move; the LLM path's "archive" is a real `shutil.rmtree`, protected only by the whole-run snapshot. A rule that promises per-item recovery has to actually do a per-item move, every time it's invoked, from every caller, not just from the deterministic one.
15. **Enforce a preview/dry-run's non-mutation guarantee at the tool-dispatch layer, not in prompt text.** Reason: the fix already exists once in this exact codebase (`set_thread_tool_whitelist` on the per-turn review fork). A "please don't" instruction to the model is not the same class of guarantee as a runtime deny, and dry-run is precisely the mode where a user is trusting the tool not to touch anything.
