### 1. Pi as a fifth provider

Pi would extend the binaries Hydra routes, but print/JSON and RPC establish transport, not enforceable permissions. Ticket 88 describes extensions with full session and tool access, so a blocking tool callback would not establish that extension code cannot act outside it. Hydra's rule is explicit: a provider it cannot gate gets a configuration root Hydra owns or is not routed (`docs/harness-spec.md`, section 2). The uncounted work is isolating all configuration and executable extension sources, proving denial and hook-failure behavior, and maintaining normalization, skills, authentication and resume support (`src/provider/mod.rs`). Build 48 needed an implementation run across 14 files, then a separate measurement phase, and uncovered three false assumptions even though Codex already spoke a supported hook dialect. API credentials would introduce a funding and secret-handling decision into a router whose design says it holds no provider credential, without evidence here that pi supplies useful work unavailable through the existing subscriptions. I would defer routing and require a pinned-version gate probe and a concrete local-model task before considering an adapter.

### 2. An own Rust harness

Putting the model loop in Hydra's core changes the promise that Hydra is a router which runs no model and holds no credential (`docs/harness-spec.md`, section 1). Rust and four tool names do not remove responsibility for malformed calls, endpoint failures, context limits, repeated calls, cancellation, bounded output, deadlines and child-process cleanup. Every accepted action must use validated arguments and an authoritative gate decision, with missing, malformed or failed gate responses denying execution before any side effect. Bash preserves the existing weakness: the gate does not interpret shell, the macOS seatbelt is not a complete boundary, and Linux launches unwrapped (`SECURITY.md`). Copy the small explicit tool surface and optional runtime, but do not copy session trees merely because both formats use JSONL: Hydra stores raw frames, derives normalized events at read time and reconstructs its own run lineage (`docs/run-record-contract.md`, sections 3 and 4). Branching model conversations would add another persistence and resume contract, while RPC adds an action entry point that the apprentice batch does not currently need. I would keep any experiment as a separate child executable, initially with print mode and linear sessions, so Hydra remains its launcher and recorder. Without evidence that the minis finish useful tasks, this harness risks becoming a maintained runtime with no capable regular user.

### 3. The smallest cut that gives the minis hands

The smallest useful experiment is a bounded loop in a disposable fixture workspace, with reads first and edits admitted only when a deterministic task requires them. The proposed endpoint shortcut is unproved: build 161 specifies an Ollama `/api/generate` shim returning response text, not OpenAI-compatible chat or structured tool calls. Ticket 87 says the local model cannot use tools reliably, reports its earlier judge result as 3 of 15, and records 17 GB of swap when Ollama ran beside agents on the 8 GB machine. Hands could let it inspect fixture files, attempt a prescribed edit and receive test feedback, but writing an answer about a command does not justify letting it launch Hydra runs or panels. A routed cut still needs a tool table and dialect, gate enforcement, raw event vocabulary and normalizer, launch metadata and terminal outcome handling; a JSONL file alone does not satisfy the record contract (`src/policy/table.rs`, `docs/run-record-contract.md`). The existing loop has earlier gaps: its README says refusal and summary templates read Claude frames only, its outcome can differ from `hydra show`, its pairs cannot enter `hydra export`, and nothing trains on them (`integrations/apprentice/README.md`). Cost in sessions is not established: build 48 documents an implementation run followed by session-led measurements for an adapter, which is evidence against promising a complete new runtime in one session, not an estimate for this task. I would measure structured action selection and task completion on fixtures before commissioning the Rust loop, then estimate implementation and adversarial validation separately from the observed failures.

### Recommendation

Defer the fifth provider and the own harness, and finish measuring the apprentice already built: compare both models on the bank, correct the grading and export gaps, then test a bounded fixture task whose success is mechanically checked. Advance only if local actions improve completion enough to justify endpoint adaptation, runtime maintenance and independent gate validation; keep the experimental executable separate from Hydra, load no executable extensions and require no persistent service for Hydra to work. A useful next result is a measured capability limit and a session estimate grounded in that experiment, rather than another provider row or a loop whose existence is mistaken for learning.
