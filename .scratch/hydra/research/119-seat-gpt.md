## 1. Accept hook-only VM runs, or keep recorded work on the Mac?

**What the code does today.** `src/sandbox.rs:46` returns `cfg!(target_os = "macos")`; `src/spawn_config.rs:121` writes a profile only when that is true and otherwise returns two `None` values. `src/pty.rs:95` launches the original binary when the profile is absent. `src/run/mod.rs:864` refuses a missing sandbox executable only on the wrapped branch. `src/record/lines.rs:52` serializes `sandbox` as an optional digest; the nonwrapped branch therefore records null, not an explicit backend or reason. This agrees with `docs/harness-spec.md:1009`, which explicitly permits Linux to launch unwrapped today. Requiring a wrapper would change current behavior, not merely clarify it.

The policy hash cannot distinguish these populations on its own. `src/policy/mod.rs:585` hashes the names and bytes of policy-directory JSON files, with lengths; the OS and sandbox implementation are not inputs. The same policy set on two systems has the same policy hash. Inventing an OS-specific value for that field would change its contract (`docs/run-record-contract.md:190`), whereas an explicit enforcement field would describe the difference directly.

Several guarantees depend on the wrapper: corpus, other spawn, pruned-record and approval-store read denials (`src/sandbox.rs:117` onward), sibling seat-socket connection denial (`src/sandbox.rs:148`), copied-skill and plugin write denials (`src/sandbox.rs:243` onward), and TIOCSTI denial (`src/sandbox.rs:110`). `inside_seatbelt()` returns false off macOS (`src/sandbox.rs:76`); the root-redirection refusal at `src/run/mod.rs:295` depends on it. Rung-two admission also executes the proposed code directly on the unwrapped branch (`src/rungs/evolve.rs:1251`). Naming the population does not replace those checks.

Two qualifications matter. First, the ticket's `cat ~/.claude/x` example overstates the ordinary seatbelt: `compose()` begins with allow-default (`src/sandbox.rs:106`) and does not generally deny reads of unrelated home files. The interactive narrowing function denies home **writes**, not all reads (`src/sandbox.rs:314`). Second, Codex's Linux branch requests its own `workspace-write` sandbox (`src/provider/codex.rs:82`), so “Hydra supplies no OS wrapper” is more accurate than saying every Linux child necessarily has no sandbox of any kind. That vendor feature is not evidence that Hydra's corpus and socket rules hold.

**Verified versus inferred.** `uname -srm` returned **Darwin 25.2.0 arm64**. A read-only Python scan found **0** mentions of `landlock`, `bubblewrap` or `bwrap` in Rust sources under `src/`. These are platform and source measurements, not a Linux launch measurement. There is an additional port prerequisite: `src/lib.rs:44` unconditionally exposes `procinfo`, and `src/procinfo.rs:23` uses `libc::KERN_PROC_PID` and Darwin-style `sysctl` structures without a target-OS guard. I infer that Linux liveness needs porting; I did not cross-compile and do not claim an observed compiler failure. The ticket's conditional launch path is real, but a working Linux Hydra binary has not been established by this review.

**Recommendation.** Keep normal recorded runs and rung-two admission on macOS until a Linux build and wrapper pass the relevant containment probes; preserve map 62's protection of evidence and map 67's narrower claim of defence behind the gate. If the human chooses an interim experiment, make it an explicitly selected, disposable VM population with no authoritative corpus or approval state, record the absence of Hydra enforcement explicitly, and keep its evidence out of ordinary Rungs learning by default.

**What would change my mind.** A measured independent VM boundary that keeps the writer, corpus, policy and approval authority beyond the provider's reach could justify that interim population without Hydra's own wrapper. Merely having a VM, a different policy hash, or a null sandbox digest would not: the VM isolates the laptop, but not the evidence writer from its own same-user agent.

## 2. Bubblewrap or Landlock, and what changes in row 4?

**What the code does today.** The profile is an ordered set of allow-default, deny-parent and reopen-child rules (`src/sandbox.rs:105` through `src/sandbox.rs:277`), not simply a workspace write allowlist. It distinguishes file data from metadata, denies Unix-socket connections under the spawn parent while reopening one socket, denies an ioctl, protects git administration files after reopening owned paths, and denies plugin-manifest components even inside writable trees. `src/spawn_config.rs:121` is the generation point, but launch wrapping lives at `src/sandbox.rs:417` and `src/pty.rs:95`; gated interactive launch has its own call at `src/interactive.rs:289`, and admission has the separate branch at `src/rungs/evolve.rs:1251`.

Row 4 is the **protected hook-config writer**, not a particular profile format. `docs/harness-spec.md:1483` and `docs/harness-spec.md:1502` make `src/spawn_config.rs` an admission-protected file; `src/rungs/evolve.rs:603` also protects the sandbox module. A Linux wrapper must remain inside this protected mechanism, including any added helper, policy compiler, seccomp program and backend-selection code. Updating only the row-4 file would leave other execution paths bare.

**Verified versus inferred.** I read all 537 lines of `src/sandbox.rs` and all 169 lines of `src/spawn_config.rs`. There is **1 implemented wrapper backend**, the hard-coded sandbox-exec wrapper; there are **0 measured Linux wrapper launches** in this review. The terminal and bounded-read kernel tests are macOS-only (`tests/sandbox_tty.rs:12`, `tests/sandbox_read_only.rs:13`). Existing test names or profile text are not a Linux parity result.

My engineering judgment is that **bubblewrap is the better starting point for this particular profile**. Mount namespaces can express a protected tree with selected writable subtrees and hidden sibling state; retaining the same paths and HOME is useful for these CLIs. Landlock is closer in being an inherited kernel restriction without requiring a new filesystem view, but its allowlist model does not directly translate an ordered deny-list with exceptions: granting an ancestor broadly cannot simply be undone by a narrower child denial. Neither choice alone establishes equivalence for terminal ioctls, inherited descriptors, path-pattern denials and seat sockets. These are design comparisons, not kernel behavior measured here; the worktree does not contain authoritative Linux API documentation or a prototype proving them.

**Recommendation.** Prototype an unprivileged bubblewrap backend plus the specific syscall restrictions needed for terminal safety, compiling one reviewed set of filesystem and socket requirements into each OS backend; refuse the launch when the required mechanisms are unavailable instead of silently falling back to hooks. Keep row 4's protected role, return a backend-tagged launch specification and digest from spawn preparation, preserve the existing digest field's compatibility, and route recorded, gated interactive and admission execution through the same backend abstraction.

Concrete acceptance work before moving real sessions:

- Check the actual distro's user-namespace availability and denial behavior at preflight; a kernel version alone is insufficient evidence. If Landlock is tested instead, probe the supported ABI and required rights and reject partial enforcement.
- Retain model-network access and the provider's own state while denying corpus, approvals, siblings and protected configuration; test ordinary paths, symlinks, hard links, renames and commands through interpreters using synthetic in-worktree fixtures first.
- Measure owned versus sibling Unix sockets and inherited file descriptors, then the terminal ioctl on a test-owned pty. A read-only bind is not evidence that a socket cannot be connected to.
- Exercise plugin and copied-skill protections after writable subtree exceptions. The current anywhere-in-path plugin-manifest rule needs an explicit Linux design, not a claim that a bind mount reproduces it automatically.
- Replace reliance on macOS's `inside_seatbelt()` with a Linux design for non-bypassable parent restrictions. An environment marker alone is not equivalent.
- Probe vendor sandbox nesting separately. Making `wraps_launches()` true on Linux currently switches Codex to `danger-full-access`; do not widen that provider by accident while introducing a backend.

**What would change my mind.** Choose Landlock if the target VM cannot support unprivileged namespaces and a capability-probed Landlock implementation, with necessary supplemental controls, passes the same filesystem, socket, terminal and launch tests with fewer exceptions. A successful “write outside workspace denied” test alone would not settle either choice.

## 3. Does provider drift need per-OS rows?

**What the code does today.** `src/provider/mod.rs:29` has a single four-entry `(Provider, version)` table, with no platform key. Launch reads the installed version using `--version` (`src/provider/mod.rs:70`, `src/run/mod.rs:372`), and the record stores that string (`src/record/lines.rs:25`). `src/doctor.rs:39` compares each installed binary with the one measured string for its provider. Neither the table nor `RunStart` records OS, architecture or a wrapper backend. Fixture directories are provider-and-version keyed (`tests/fixture_corpus.rs:16`).

Map notes at `.scratch/hydra/map.md:187` already say version is not the only source of drift. This becomes concrete across platforms: Codex launch flags differ by `wraps_launches()` (`src/provider/codex.rs:82`), the hook uses an absolute Python interpreter (`src/policy/gate.py:1`), and the new wrapper would affect filesystem and process behavior before the model acts. Equal version strings cannot prove equal hooks, login behavior, subprocess support or confinement.

**Verified versus inferred.** A source-table count returned **4 provider rows**. Recursively inspecting the synthetic record corpus found **5 directory labels**: four provider/version labels and `harness`, with **0 OS-specific labels**. I did not run provider version commands or drift tests: they invoke provider binaries, and the task asks for provider-free checks. Linux arm64 distribution availability remains the ticket's supplied premise, not a result of this seat's work.

**Recommendation.** Keep one maintained table but key measured support by provider, OS and architecture, with observed version, date and probe results; keep reading the actual version each session and at launch. Add platform and enforcement facts to new records, and require Linux arm64 evidence independently of macOS arm64 or Linux x86_64 before marking that row supported.

**What would change my mind.** Repeated paired measurements could justify sharing particular protocol expectations across platforms, and identical bytes can share fixtures. They would not remove the need to know which platform and backend produced a result; an unmeasured row should say unmeasured, not inherit a Mac pass.

## 4. Mixed-machine records, doctor, Rungs, and base_tree

**What the code does today.** `base_tree` is the content tree at seeding, not machine identity (`src/record/lines.rs:105`); the same source tree on two machines can have the same value. It may be null, and its object can be garbage-collected. `docs/run-record-contract.md:196` states those limits. Keeping only its hash neither preserves the underlying objects nor makes an imported record's worktree paths usable.

The walk takes one local layout, enumerates its immediate `.jsonl` files and normalizes them against locally discovered policies (`src/walk.rs:48`, `src/walk.rs:64`, `src/walk.rs:114`). That can read historical event bytes without the original process, but policy replay is not wholly portable. `ReplaySpawn::of` prefers recorded scopes and reconstructs missing ones (`src/normalize/mod.rs:826`); its snapshot still comes from the reader's layout (`src/normalize/mod.rs:898`). The policy compiler's deny list also uses the reader's layout and `hydra_home()` (`src/policy/mod.rs:794`). `GateMark::of` treats a regenerated digest mismatch as foreign (`src/normalize/mod.rs:746`), which appropriately limits conclusions but does not reproduce the original enforcement.

Rungs calls `live::scan` before selecting records (`src/rungs/corpus.rs:234`). For a file without `run_end`, `src/live.rs:192` queries the **local** kernel using recorded PID and start time. A VM process may therefore appear abandoned on the laptop; a coincidental local match could instead appear live. Rungs explicitly permits abandoned provider records as learning input (`src/rungs/corpus.rs:324`) and has no sandbox-strength exclusion in `judge()` (`src/rungs/corpus.rs:314`). Merely labeling a hook-only population does not stop it affecting learning. Rung two needs local source objects and checkout context to reconstruct a proposal (`src/rungs/evolve.rs:537`), so JSONL backup alone is not portable admission or recovery.

**Verified versus inferred.** A read-only Python traversal of `tests/fixtures/records/**/*.jsonl` parsed **12 files, 12 run starts, 12 distinct run IDs and 11 closed records**. All **12** omit `sandbox`; **1** carries `scopes`; **0** carries any of the checked origin keys (`host_id`, `origin`, `platform`, `os`, `arch`, `machine_id`). These are synthetic legacy-shape measurements, not a live corpus walk or proof that mixed-machine replay works. The initial nonrecursive glob returned zero because the fixtures are nested by provider/version; the recursive count above is the relevant result. I did not run `hydra doctor --walk`, which targets the runtime corpus outside this worktree, nor cargo tests that would write additional files or use scratch roots outside it.

**Recommendation.** Treat the laptop copy as an archive, keep VM execution and authoritative Rungs processing on the VM initially, and add an explicit origin ID plus platform/enforcement provenance before pooling corpora; preserve UUID run IDs and deduplicate exact copies without rewriting recorded paths. For active mixed-origin learning, make unfinished foreign records “remote state unknown” rather than locally abandoned, partition evidence by enforcement population, and report replay limits instead of inferring a gate leak from local reconstruction.

Back up completed records through atomic publication; if open records are copied, keep them outside local lifecycle management until an authoritative final version arrives. Detect conflicting bytes for the same run ID rather than overwriting silently. Preserve the skill-store history and required source objects separately if reproducible replay or diff recovery is wanted; `base_tree` is only a reference. An archive copy must not cause local stop, harvest, prune or reap operations to act on foreign PIDs or recorded paths. Schema additions should keep absent legacy provenance as unknown, not infer it from a path prefix or sandbox null.

**What would change my mind.** If the laptop is strictly an inert backup and nobody points doctor, Rungs or lifecycle commands at it, a backup-only workflow needs no immediate reader changes. Before recommending a pooled corpus, I would want portable fixtures from both platforms showing stable normalization and explicit limits, one open remote record that is never called abandoned locally, duplicate/conflict handling, and a restored diff whose referenced objects really exist.

## Recommendation summary

1. Keep ordinary recorded runs and admission on the Mac until Linux enforcement is measured; any interim VM experiment must be explicit and isolated from authoritative learning.
2. Prototype bubblewrap with the necessary supplemental controls; protect the whole backend and cover every execution path without hook-only fallback.
3. Use one measurement table keyed by provider, OS and architecture, and record platform plus backend on each new run.
4. Use one-way archival backup first; pooled doctor/Rungs use needs origin-aware liveness, evidence provenance and portable replay, which base_tree does not supply.
